# 变更策略（CHANGE_POLICY）

> **一句话**：只改"完成当前任务所必需的那几行"，其余一律不动。
>
> 本文件是**变更范围的单一来源**。其他文件（`CLAUDE.md`、`SKILL.md`、模板）只引用，不复制。

---

## 1. 适用范围

任何对仓库内容的修改，包括但不限于：源码、头文件、脚本、配置、构建文件、测试、
文档、`.ioc` / `.uvprojx` 等生成器配置。

**不适用**：纯只读操作（查看、搜索、运行不写文件的检查）。

---

## 2. 核心原则：最小合理差异

"最小"不等于"最少改动"，而是**最少且充分**：

| 维度 | 要求 |
|---|---|
| 改哪些文件 | 只改完成任务**必须**改的 |
| 每个文件改多少 | 只改**必须**改的那几行 |
| 改动的形态 | 与周围代码**同风格**（命名、缩进、注释密度、错误处理方式） |

---

## 3. ✅ 允许

- 为完成当前任务所必需的功能性改动
- 修复因本次改动而**直接产生**的错误
- 补充与本次改动**直接相关**的最小注释
- 新增文件（优先新增，而非改已有文件）

## 4. ❌ 禁止（除非任务明确要求，且已获授权）

| 禁止项 | 为什么 |
|---|---|
| 无关重构（重命名、拆函数、换设计模式） | 让 diff 变大，回滚变难，评审失去焦点 |
| 全局格式化 / 批量改缩进 / 改行尾 | 产生大量噪音 diff，淹没真实改动 |
| 顺手升级依赖、改工具链版本 | 引入与被测问题无关的变量 |
| 批量改注释、翻译注释、统一术语 | 同上 |
| 删除"看起来没用"的代码/文件 | 可能是用户的备份或特例处理 |
| 修改与任务无关的测试 | 掩盖失败的唯一方式就是改测试 |
| 改 `.gitignore` 来"甩掉"不该提交的文件 | 治标；应修内容而不是藏起来 |

> **前后端/工具链风格不统一时**：跟**你正在改的那个文件**保持一致，不要顺手"修正"别的文件。

---

## 5. 🔒 任务前状态检查（强制）

**任何修改之前必须先做，并把结果作为基线记录下来**：

```bash
git status --short          # 有没有未提交的东西？是谁的？
git diff --stat             # 未提交改动的规模
git log --oneline -3        # 当前 HEAD
```

**判据**：

- 若已存在**未提交修改**且**与本次任务无关** → **不得覆盖、不得清理、不得顺手提交**；
  只在其之外工作。若任务需要碰这些文件 → **先报告冲突风险，等确认**。
- 若已存在未提交修改且**与本次任务相关** → 它是**用户的工作**，
  在其基础上做最小增量，**不要回退重来**。

---

## 6. 🚦 变更规模红线（触发即**暂停并报告**）

出现以下任一情况，**停下来报告**，不要继续扩大改动：

| 红线 | 默认阈值 |
|---|---|
| 实际改动文件数 **>** 计划文件数 × 1.5 | 或 > 计划 + 3 |
| 新增行数 **> 200**（不含新建文档） | — |
| 触及**计划外**的目录（如改了硬件配置、生成代码、CI） | 一律报告 |
| 需要"顺便"改公共接口 / 被多处引用的函数 | 一律报告 |
| 发现原计划无法完成（需要更大重构） | 一律报告 |

**报告格式**：计划 vs 实际 / 超出原因 / 影响面 / 建议（继续 / 缩小范围 / 拆成两轮）。

---

## 7. 验收标准（可检查）

一次变更**只有同时满足**下列各项才算合规：

- [ ] 任务前做过状态检查，基线已记录
- [ ] `git status` 里**没有**计划外的文件被修改
- [ ] `git diff` 里**每一处改动**都能对应到任务要求（说不出理由的改动 = 违规）
- [ ] 没有出现全局格式化 / 重命名 / 依赖升级
- [ ] 未触碰 `.gitignore`、生成代码、硬件配置（除非任务明确要求）
- [ ] 触及规模红线时，已暂停并报告过
- [ ] 未提交任何东西（除非获授权）
