# Autolab 架构与可移植性

> 这份文件回答三个问题：**换工程文件夹**、**换电脑**、**换芯片家族**，这套闭环还能不能用。
> 它讲的是**方法**，所以放在跨工程的 `~/embedded-ai-journey/`，不放进某个工程里。

---

## 一、先说清楚：它现在持久化在哪（事实，不是印象）

| 内容 | 位置 | 换文件夹 | 换电脑 |
|---|---|---|---|
| 工具 / 测试 / CLAUDE.md / hook | **工程仓库**（跟着工程走） | ❌ 不带过去 | ❌ |
| 能力进度 / 学习 / 测试契约 / 决策 | `~/embedded-ai-journey/AUTOLAB_*.md` | ✅ 带 | 手动拷 |
| 流程定义（技能） | `~/.claude/skills/ai-embedded-autolab` | ✅ 带 | 手动拷 |
| AI 的"项目记忆" | `~/.claude/projects/<工程路径>/memory/` | ❌ **按工程路径隔离** | ❌ |

**两个必须知道的事实：**

1. **AI 的项目记忆是按工程路径隔离的** —— 换一个文件夹，AI 就"不记得"上一个工程的事。
   它不会自动跟着走。
2. **本工程至今没有往那里写过任何东西**（目录是空的）。
   **这套闭环一点都没进"AI 记忆"，它活在工程仓库和 `~/embedded-ai-journey/` 里。**
   —— 这其实是好事：**记忆不可版本控制、不可审阅，而文件可以。**

> 结论：**不要指望"记忆"来承载这套东西。要指望"目录 + 文件"。**

---

## 二、分层：哪一层是通用的，哪一层是"适配器"

跑通一次闭环要四件事：**造出来 → 装进去 → 动起来 → 看结果**。逐层看：

| 层 | 做什么 | 通用 or 适配器 | 本工程实现 |
|---|---|---|---|
| **构建** | 源码 → 固件 | 🔌 **适配器** | Keil `uVision.com -b` + 四判据 |
| **烧录 / 复位** | 固件 → 板子 | 🔌 **适配器** | Keil `-f`（Reset&Run）+ 串口 ESC 软复位 |
| **调试 / 取现场** | 读寄存器、内存、故障 | 🔌 **适配器** | ST-Link + `pyocd` |
| **串口观测** | 激励 + 收数据 | ✅ 通用 | `serial_tool.py` |
| **判定** | PASS / FAIL | ✅ 通用 | `pytest` + 退出码约定 0/1/2 |
| **取证 / 报告 / 停止条件** | 失败留下现场 | ✅ 通用 | `hil.py` |
| **CI** | 提交即自动检查 | ✅ 通用 | git hook（层1）+ 流水线定义（层2） |
| **配置源一致性** | 生成器 ↔ 代码 | 🔌 **适配器** | CubeMX `.ioc` ↔ 代码 |

**记住这条分界线：**
> **"怎么造/怎么烧/怎么看寄存器"是适配器；
> "怎么激励、怎么判、怎么留证据、怎么停"是骨架。**

**生态越不成熟，骨架越重要** —— 因为适配器可能根本没有好用的现成工具，
你只能靠"无板层"（构建本身 + 宿主机单元测试 + 静态契约）兜住大部分验证。

## 三、换工程文件夹（新项目）怎么做

**不要重头写。** 正确姿势：

1. 新工程里建同名结构：`tools/` `tests/` `CLAUDE.md` `pytest.ini` `requirements.txt`
2. **搬骨架**（通用件，几乎不用改）：
   `serial_tool.py`、`hil.py`、`pre-commit`、`pytest.ini` 的结构、报告模板、停止条件
3. **换适配器**（必须重写）：
   `build.py`（新工具链的四判据）、烧录命令、`debug_probe.py`（新 probe）、`check_*.py`
4. **重写 `CLAUDE.md` 的"会咬人的坑"一节** —— 每换一个工程/一块板子，坑都不一样
5. **改判定阈值**：`build.py` 的编译动作数下界、`test_static.py` 的内存预算，都要按新工程**重新标定**

> **标定纪律不迁移**：新工程的每一条判据，都要**亲手制造一次失败**看它会红。

→ 所以真正的答案是：**把骨架抽成一个模板目录**（见第六节），新工程拷贝后只写适配器。
   **这份文件就是模板的设计说明。**

## 四、换电脑怎么做（目标：人工操作尽量少）

**现实：只要 Keil 还在链路里，就不可能一键迁移。** Keil 是系统级安装 + 授权，pip 装不了。
但可以把"能自动化的部分"做到位：

### 需要人工做的（无法避免）
1. 装 **Keil MDK**（+ ARMCC AC5），确认 `UV4\uVision.com` 和 `ARMCC\bin\fromelf.exe` 的位置
2. `python -m pip install -r requirements.txt`

### 应该能"一条命令告诉你还差什么"的
3. **`python tools/preflight.py`** —— 逐项检查环境（Keil 路径 / pip 依赖 / 串口 / 调试器 /
   工具链可执行文件），对缺失项**直接打印可复制的修复命令**

### 拷贝过去的
4. 工程仓库（含 `tools/` `tests/` `CLAUDE.md`）
5. `~/embedded-ai-journey/`（能力进度）
6. `~/.claude/skills/ai-embedded-autolab`（流程定义）

### 为此要做的加固（当前**未完成**）
- [x] `requirements.txt` 锁定 pip 依赖
- [ ] **把所有写死的本机路径改成"环境变量 + 默认值"**
      当前还有两处没加覆盖：`tools/debug_probe.py` 的 `FROMELF`、
      `tools/hil.py` 的 `UVISION`（`tests/test_static.py` 已经支持 `AUTOLAB_FROMELF`）
- [ ] **`tools/preflight.py`**（上面第 3 条）

## 五、换芯片家族怎么做（含"生态不成熟"的国产芯片）

**结论：骨架完全适用；适配器要重写一套。** 按第二节的分界线照抄即可。

### 每个芯片家族需要重新提供的"适配器"
1. **构建**：工具链 + 四判据要**重新标定**（退出码含义、日志格式、产物路径都不一样）
2. **烧录 / 复位**：厂商下载工具，或 openocd / pyocd 的对应 target
   - ⚠️ **一个现实难点**：pyocd/openocd 对国产片的支持**经常缺失或不完整**
     → 这一层可能只能退回"厂商 PC 工具 + 人工点一下"
3. **调试**：没有 SWD 就没有 `debug_probe.py` 的等价物
   → **故障取证能力会显著下降**，这时更要靠"把故障状态打印出来"的自诊断代码
4. **配置源一致性**：每家生成器不一样（CubeMX / MCUXpresso / 各家自家 IDE）

### 生态不成熟时，重心要往"无板层"挪
| 层 | STM32（生态成熟） | 国产/不成熟 |
|---|---|---|
| 无板层（构建 + 宿主机单测 + 静态契约） | 一层 | **主力** —— 因为硬件层可能根本不可靠 |
| 真机层（烧录 + 串口 + 调试） | 完整 | 可能只剩"串口"，甚至全人工 |

> 反过来说：**正因为生态不成熟，越要把"可测的纯逻辑"抽出来在 PC 上测**
> （本工程的 `ringbuf.h` 就是这个套路 —— 它跟芯片无关，换任何芯片都能原样复用）。

### 你提的思路是对的，落地方式如下
**保持骨架 + 每家族一套适配器 + 把踩过的坑回写。** 目录结构建议见第六节。

## 六、建议的目录结构

```
~/embedded-ai-journey/
├── AUTOLAB_PROGRESS.md          # 能力进度（跨工程）
├── AUTOLAB_LEARNING.md          # 学习记录（跨工程）
├── AUTOLAB_TESTS.md             # 测试契约（跨工程）
├── AUTOLAB_DECISIONS.md         # 工程决策（跨工程）
├── AUTOLAB_ARCHITECTURE.md      # ← 本文件：方法本身
├── skeleton/                    # ★ 通用骨架（拷贝进新工程）
│   ├── tools/serial_tool.py     # 通用：串口激励+观测
│   ├── tools/hil.py             # 通用：编排 + 取证 + 报告 + 停止条件
│   ├── tools/hooks/pre-commit   # 通用：提交前自动跑无板层
│   ├── pytest.ini               # 通用：testpaths + 分层标记
│   ├── requirements.txt         # 通用：pip 依赖
│   └── CLAUDE.md.template       # 模板：坑要各工程自己填
└── adapters/                    # ★ 按"芯片家族"存适配器与坑
    ├── stm32-keil-ac5/          #   本工程这一套
    │   ├── build.py             #     Keil 四判据（退出码/日志/编译动作/产物时间戳）
    │   ├── flash.sh             #     uVision.com -f
    │   ├── debug_probe.py       #     pyocd 封装
    │   ├── check_ioc.py         #     CubeMX .ioc ↔ 代码
    │   └── PITFALLS.md          #     这个家族的坑（8MHz 晶振、GBK、CubeMX 覆盖…）
    ├── gd32/                    #   兆易等 ARM Cortex-M 国产片（可复用大部分）
    ├── riscv-vendor/            #   RISC-V 家族（适配器几乎要重写）
    └── ...
```

**新工程 = 拷 `skeleton/` + 挑一个 `adapters/<family>/` + 填 `CLAUDE.md` 的坑。**

## 七、规则：每踩一个新坑，回写到哪里

| 坑的类型 | 写到哪里 | 为什么 |
|---|---|---|
| **这个芯片家族的**（时钟、外设怪癖、厂商工具） | `adapters/<family>/PITFALLS.md` | 换同家族工程能直接复用 |
| **这个工程的**（板子接线、波特率、业务逻辑） | 工程的 `CLAUDE.md` | 只对本工程有效 |
| **方法层面的**（怎么测、怎么判、怎么不踩） | `AUTOLAB_LEARNING.md` | 跨工程、跨芯片都成立 |
| **一个决定及其取舍** | `AUTOLAB_DECISIONS.md` | 下次遇到同样选择不用重新想 |

> **判据**：**这条经验，下一个用别的芯片的项目还用得上吗？**
> 用得上 → 写进 LEARNING / ARCHITECTURE；用不上 → 写进 adapters 或工程 CLAUDE.md。

## 八、一页速查

| 场景 | 要做的 |
|---|---|
| 换工程文件夹 | 拷 `skeleton/` → 挑 `adapters/<family>/` → 重写 `CLAUDE.md` 的坑 → **重新标定所有判据** |
| 换电脑 | 装 Keil + `pip install -r requirements.txt` + 跑 `tools/preflight.py` → 拷工程与 journey 目录 |
| 换芯片家族 | 骨架不动；重写构建/烧录/调试/配置检查四个适配器；**把重心挪向无板层** |
| 踩了个新坑 | 按第七节的表回写；**别只留在聊天记录里** |
